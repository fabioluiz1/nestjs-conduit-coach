# Q03 — Entity decorator vs DB column (data model: entity vs DB)

## Question (as asked)

You change `Article.body` from `@Property({ fieldName: 'body' })` (string) to
`@Property({ type: 'text', fieldName: 'body' })` in `article.entity.ts` and restart the backend.
Does the MySQL column change? **Yes or no, and exactly why?**

## Candidate's answer (initial)

No. (1) `npx mikro-orm migration:create`, (2) wire the migration file into
`backend/mikro-orm.config.ts`'s `migrationsList`, then one of (3) `migration:up` or restart the
backend.

## Coach pushback + resolution

**Pushback 1 — the "why," not the procedure.** Candidate gave the steps to *make* it change but
not why the restart-with-decorator-only does nothing. Candidate's second attempt drifted into
save-time behavior ("varchar(255) will cut off / trim the value"), which is (a) the wrong layer for
this question and (b) factually off.

Coach pointed to `01-COACH.md:845-852` (Concept 3) with the narrowest lines:
- `:847` — entities are decorator-annotated classes → decorator is *mapping metadata*.
- `:849` — migrations' `up()` emits DDL, only run if registered → DDL is the only thing that alters
  the live schema.
- `:851` — `onModuleInit()` runs `migrator.up()` on every boot → restart runs *registered
  migrations*, not the entity edit.

**Candidate (corrected):** "Because the database only changes if a migration file exists and is
registered in the `migrationsList`." ✅ — no registered migration → no DDL executes → column
untouched; the decorator only changed MikroORM's mapping metadata.

**Pushback 2 — factual, the truncation claim.** Coach flagged "cut off / trim" as the non-strict
behavior and noted this fact is **not in the coach docs** — posed as a pull from the candidate's own
MySQL knowledge: what does strict mode (5.7+ default) do on a 600-char insert into `varchar(255)`?
**Candidate:** "database error." ✅ — Error 1406, "Data too long for column"; not silent truncation.
Practical note for verify: before the migration, an over-length insert errors (500/DB error), it
doesn't quietly lose data.

## Coach verdict

**Correct** after two pulls. Conceptual: schema changes only via a registered migration's DDL; the
decorator is mapping metadata that emits no `ALTER`. Factual: strict-mode MySQL rejects the
over-length insert (Error 1406) rather than truncating.
