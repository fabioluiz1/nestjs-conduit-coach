# Q04 — Migration registration gotcha

## Question (as asked)

You write `backend/src/migrations/AlterArticleBodyDescriptionToText.ts` with the correct
`ALTER TABLE` DDL. You restart the backend. The migration **does not run**. What's missing, and in
which file?

## Candidate's answer

It's necessary to register it into `migrationsList` of `backend/mikro-orm.config.ts`.

## Coach pushback + resolution

**Pushback — the "why."** Coach: right file and action, but why doesn't MikroORM auto-discover the
file sitting in `backend/src/migrations/`? What setting forces explicit registration?

**Candidate:** It doesn't auto-discover because `discovery: { disableDynamicFileAccess: true }`. We
prefer manual registration for a reason: in AWS Lambda the migration files won't survive into the
bundled deployment — there will be no file to auto-discover. We list them in `migrationsList` so
MikroORM knows the full set and runs the pending ones.

## Coach verdict

**3-star.** Got the setting (`disableDynamicFileAccess: true` → no filesystem globbing) **and** the
rationale: in a bundled deploy (Lambda/webpack/esbuild) loose migration files aren't discoverable,
so the explicit `migrationsList` is the bundle-safe manifest of what exists and what to run.
