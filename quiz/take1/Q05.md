## Question (as asked — final form)

`npx mikro-orm migration:create --name AlterArticleBodyDescriptionToText` generated this (verbatim,
real run against the seeded DB). You're reviewing the tool's output before it ships. **Ship as-is,
fix, or reject — and justify.** *(Angle: reviewing AI/CLI-generated output — not registration,
which Q4 settled.)*

```ts
async up()  { this.addSql('alter table `article` modify `description` text not null, modify `body` text not null;'); }
async down(){ this.addSql('alter table `article` modify `description` varchar(255) not null, modify `body` varchar(255) not null;'); }
```

## Candidate's answer

`MODIFY` is correct — it changes the column definition. `varchar(255)`→`text` is correct: 255-char
content fits in a TEXT column. I'd test whether the rollback is safe — does `MODIFY ... varchar(255)`
on a column that may now hold large text safely trim back? In strict mode I'd bet it errors and the
rollback fails. So for a safer rollback I'd first run an UPDATE to trim any rows > 255 chars.

## Coach verdict

**3-star diff review.**
- **Verdict: ship the `up()`** — `ALTER … MODIFY` (table exists, so not CREATE/DROP), target `text`,
  both columns, `not null` matching the entity. Correct **recognition**, not recall.
- **`down()` hazard** — correctly flagged that reverting `text`→`varchar(255)` errors in strict mode
  (Error 1406) once long bodies exist; the rollback isn't safe to assume. Strongest-reviewer catch.
- **Coach refinement:** pre-trimming rows to fit is *data loss* — a `down()` that can't run on
  overflowing data is a known migration limitation, usually accepted/documented rather than silently
  patched.
