# Q01 — Story → technical change (long-form articles)

## Question (as asked)

The first story: authors writing **long-form articles**. Name the technical change it requires,
explain why the story demands it, and name the file that proves the gap exists today.

## Candidate's answer

Long form articles requires TEXT (64KB) or MEDIUMTEXT/LARGETEXT columns, otherwise their
contents will cut off.

Medium posts can be small; however their audience may demand longer / elaborated contents that
fit better in TEXT columns. A 64KB size seems good enough for a blogging platform.

We can confirm the gap exists in the
`backend/src/migrations/InitialMigration.ts` file:

```
'create table `article` (`id` int unsigned not null auto_increment primary key, `slug` varchar(255) not null, `title` varchar(255) not null, `description` varchar(255) not null, `body` varchar(255) not null, `created_at` datetime not null, `updated_at` datetime not null, `tag_list` text not null, `author_id` int unsigned not null, `favorites_count` int not null) default character set utf8mb4 engine = InnoDB;',
```

Both description and body are limited to 255 chars which may not be enough.

In order to change the column size, it's necessary to edit the entity file
`backend/src/article/article.entity.ts`:

```
@Property({ fieldName: 'body' })
body = '';
```

to

```
@Property({ type: 'text', fieldName: 'body' })
```

OPTIONAL: adjust `@Property({ fieldName: 'description' })` to a bigger size (not 255; but not text
— 1024 may be a better fit). PRO: simple adjacent change; CON: scope creep.

In order to make the change effective: `npx mikro-orm migration:create` → this creates a new file
in `backend/src/migrations`. Finally, the file must be registered in
`backend/mikro-orm.config.ts`'s `migrationsList`. The migration runs by either
`npx mikro-orm migration:up`, or simply rebooting the app because `backend/src/app.module.ts`
automatically invokes `getMigrator().up()`.

## Coach verdict

**3-star derivation. Correct and complete.** Named the change (`varchar(255)` → `TEXT`), the
rationale, and proved the gap with the actual DDL. Bonus: front-ran Q3 (entity edit) and Q4
(`migrationsList` registration + boot-time `getMigrator().up()`) — both correct, to be
re-confirmed at their questions. 64KB/MEDIUMTEXT awareness is a bonus; TEXT is the right call for
a blog body.

## Coach pushback + resolution

Flagged the `description` → `varchar(1024)` fork as a real design judgment (not an error) that
belongs in `plan.md` Decisions with a rationale. Pull question posed: which is the cleaner line to
defend to the grader — one consistent type for both columns, or two different caps?

**Candidate:** Different caps. `body` must be `TEXT` (the actual post content). `description` stays
`varchar(1024)` — still reasonable to index for SQL query searches; descriptions hold summaries
that are good candidates for simple (not full-text) queries.

**Coach:** 3-star Plan Soundness rationale. The decisive technical reason is indexability — InnoDB
can't index a `TEXT` column without a prefix length, but `varchar(1024)` takes a normal index, so a
queryable/sortable summary stays cheap. Stated alternative (both → `TEXT`) + concrete technical
reason = grader-defensible. Record in `plan.md` Decisions.
