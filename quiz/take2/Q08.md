# Q08 — AWS stateless constraint (in-memory uniqueness)

## Question (as asked)

You're asked to "validate uniqueness of article titles." You implement it with a module-level
`const seenTitles: string[] = []`, pushing each new title on every create. It works in local dev.
In production on **ECS Fargate with 3 instances**, what breaks — and what's the fix?

## Candidate's answer

Each Fargate instance has its own copy of the array — unaware of the `seenTitles` living in another
instance. The right place to validate uniqueness is the database, with a unique index.

Fix: change the entity to make `title` unique (ask Cline to write it), run `mikro-orm migration:create`,
register the migration in `migrationsList`, restart to migrate up, then ask Cline to test via curl.
Check if it's a 500. Check the controller has `@UsePipes` on create/update (probably there since we
added `@IsNotEmpty`); the expected error is 400 (BAD_REQUEST).

## Coach pushback (the misconception)

Core answer 3-star (own-copy-per-instance → DB unique constraint, with the Concept-3 mechanics). But
the last lines conflate two things: `@IsNotEmpty()` / `@UsePipes` validates the **DTO shape** (is the
body empty?), **not** uniqueness. A duplicate title is a well-formed, non-empty string — it passes the
pipe and dies at the **DB insert**. Unhandled, that surfaces as a **500**, not 400. So what would you
*add*, and where, to turn the raw DB violation into the clean `{ errors: { field: [...] } }` shape?

## Candidate's response

Agreed — validations live at the DTO level; data-integrity constraints live at the entity/DB level.
Asks: does `01-COACH.md` document how to bind a DB uniqueness error to a field so the API knows which
field violated?

## Coach resolution

Honest answer: **not in the docs, and not an existing repo pattern** — it's net-new design (a prime
"introduce a new technical pattern" candidate). The landscape: DB unique constraint = source of truth
(race-proof); translate the violation to the error shape at the HTTP boundary; an async DTO-level
uniqueness check reintroduces the cross-instance race (Q8's own lesson) so it can't be the guarantee.

## Outcome

- **Q8 core: 3-star** (stateless constraint → Aurora unique constraint).
- The exception-handling sub-thread was spun out of the quiz and developed into coach material —

  ("HTTP lives at the boundary, not in services"), plus a **verified spike** (MikroORM metadata
  doesn't store auto-generated constraint names → mandate explicit `@Unique({ name })`) and a
  **tested custom ESLint rule** to enforce it (`backend/eslint-rules/require-named-unique-constraint.js`).
