# Q09 — Frontend API layer: Result vs plain-throw

## Question (as asked)

`frontend/src/services/conduit.ts` has two patterns: some functions return a plain decoded value
(throw on error), others return `Result<T, GenericErrors>`. Which do `createArticle`/`updateArticle`
use, and why is that the right choice for this story (empty-title/body rejection)?

## Candidate's answer 1

These services try/catch errors and code them as monads. It's the right choice because the frontend
components need to render the results, or render caught errors — this way an exception will never
crash a user-facing frontend.

## Coach pushback (finish the "why for THIS story")

Pattern ID correct (`Result`), but "renders errors / never crashes" is generic. Finish three things:
(1) what does the `Err` branch carry concretely, and how does the editor consume it per-field?
(2) why do the *other* functions (e.g. `getArticles`) just throw? (3) precision: the throwing
functions still throw — what does `.match({ ok, err })` *force* that a `try/catch` lets you forget?

## Candidate's response (complete)

1. The service uses `genericErrorsDecoder` to decode the Axios response into `GenericErrors`: a dict
   where keys are the article fields and values are arrays of errors per field. `ArticleEditor` passes
   the errors to a `GenericForm`, rendered as `<Errors errors={errors} />`.
2. `getArticles` has no per-field errors to show. A failure there isn't something the user can fix and
   resubmit — it's a real exception, a 500 page. In `ArticleEditor` the validation errors *are*
   fixable → the user needs the UI feedback to know which validations failed.
3. Monad/`match` forces transforming exceptions into handlers that render success/error components for
   the user, instead of error pages.

## Coach grade

**3-star, complete.** Correct pattern (`Result<T, GenericErrors>`), correct contrast on the right
axis (**user-fixability** decides throw vs `Result`), and the compiler-forces-both-branches safety.

## Optional bonus pull (offered, Q9 already closed) — taken, and it surfaced a real bug

**Candidate** read `buildError` exactly: `result[prop + constraint[0]] = ${constraint[1]}` →
`Record<string, string>`, key = property+constraint, value = message (same prop can fail multiple
constraints). Was honest it wasn't certain whether `verify` *wraps* the string into `["…"]`, and
raised a strong counterpoint: the MVP shipped with user-DTO validation, so it "must work."

**Coach verified it (source + live curl), settling the gut:**
- `genericErrorsDecoder = dict(array(string))` (`frontend/src/types/error.ts:3,5`) → values must be
  `string[]`. `<Errors>` (`Errors.tsx:6-9`) calls `fieldErrors.map(...)` → also assumes arrays,
  prints the compound key verbatim (no unwrap).
- Live backend: `{"errors":{"usernameisNotEmpty":"username should not be empty", …}}` → strings.
- `decoders` does NOT coerce: `array(string).verify("…")` **throws**. The throw is inside the
  `catch` of `createArticle`/`updateArticle` (`conduit.ts:84,99`) → escapes unhandled → `.match({ err })`
  never runs → field errors don't render → **AC3 fails**.
- Same code path is shared by `login`/`signUp`/`updateSettings` (`conduit.ts:41,64,74`) → the
  **shipped MVP's user validation carries the same latent bug**. Lesson: *"it shipped" ≠ "it works"*
  — distrust the "MVP must work" assumption for a path nobody exercised with empty input.

**Build implication:** fix `buildError` to emit `{ [field]: [message] }` (`string[]`, bare-field key)
— shared-pipe blast radius (Q6) that also fixes the user endpoints — a `plan.md` Decision.
