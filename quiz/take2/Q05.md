# Q05 — Review the generated migration (ship / fix / reject)

## Question (as asked)

After the entity change, you run
`npx mikro-orm migration:create --name AlterArticleBodyDescriptionToText`. It emits this (verbatim,
captured from a real run against the seeded DB). You're reviewing what the tool generated **before
it ships**:

```ts
async up(): Promise<void> {
  this.addSql('alter table `article` modify `description` text not null, modify `body` text not null;');
}
async down(): Promise<void> {
  this.addSql('alter table `article` modify `description` varchar(255) not null, modify `body` varchar(255) not null;');
}
```

**Ship as-is, fix, or reject — and justify your verdict.** *(Angle: reviewing AI/CLI-generated
output — not the registration mechanic, which Q4 covered.)*

## Candidate's answer 1

`MODIFY` is correct — it changes the column definition. `varchar(255)`→`text` is correct: 255-char
content fits in a TEXT column. I'd test whether the rollback is safe — does `MODIFY ... varchar(255)`
on a column that may now hold large text safely trim back? In strict mode I'd bet it errors and the
rollback fails. So for a safer rollback it's necessary to consider if the data loss is acceptable.

## Coach pushback 1

Strong recognition (MODIFY not CREATE; `varchar`→`text` round-trips; caught the `down()` hazard —
MySQL Error 1406 in strict mode once long bodies exist). But you stopped short of the actual ask:
**ship / fix / reject**. Is the `down()` hazard a reason to **fix** the migration (edit `down()` to
pre-trim rows), or an inherent limitation you **ship with** and document? Net it out — ship, fix, or
reject?

## Candidate's answer 2

Rollback scripts must be runnable in order to be shippable. Ship is not an option — if shipped as is
and rollback is necessary, `down()` fails when a value larger than 255 chars already exists. Reject
is not an option either — we need to ship the feature. **Answer is fix.**

Rollback must have extra verifications:
1. Create a backup table → `articles_rollback_backup_for_long_descriptions`
2. Copy only the values that exceed 255 chars

For 1 and 2 I would ask Cline to: (1) only create a new table if offending rows exist; (2) write the
copy script; (3) test the rollback by inserting a 1000-char row and executing migrate down (offending
row → backup gets exactly one row; no offending row → backup not created).

This migration strategy grants no data loss. The backup table gives a recovery path and can be
dropped after a roll-out period.

## Coach pushback 2

Hazard-detection 3-star, but the verdict swung into over-engineering. Run your own design through
three tests: (1) Does it even achieve "no data loss"? — the live `article.body` still loses the
value (it's trimmed/removed from the live column so the ALTER succeeds; you kept a side copy).
(2) Bug to fix, or physics to document? — no `down()` can revert `text`→`varchar(255)` while keeping
a 1000-char body *in that column*; it doesn't fit. (3) Cost in a 4-hour exam graded on Velocity +
Code Quality — a conditional, insert-tested backup `down()` is bespoke, rarely-run, bug-prone code;
"modify, don't rebuild / recognize when it's good enough" is the graded skill. Rubric line:
pre-trimming is data loss "usually accepted as a migration limitation, not silently patched." Re-land
it — ship, fix, or reject, and where does the caveat go?

## Candidate's answer 3

"No data loss" → if we run the rollback as is it fails 1406, so rollback is broken and can't ship. To
make it runnable, values must be trimmed to 255 — this causes data loss. Preventing data loss
requires a backup table. I would not stop documenting it, because data loss is user-facing. The cost
of a backup table is easily achievable if Cline creates a table with only the offending records —
allowing users to recover during a roll-out period.

**One-line verdict: Fix the rollback script to have a recovery mechanism for offending rows only.**

## Coach pushback 3

What you have right: the `down()` is lossy and that must never be *silent* — document it. Where the
call goes wrong — premise "rollback must be runnable to be shippable → bake a backup table into
`down()`" breaks on two grounded facts: (1) **`down()` never runs automatically here** — rollback is
manual, single-runner, deliberate (`01-COACH.md:869`: "invoked manually from a single runner, never
automatically"), so there is always a human in the loop who can snapshot first. (2) **The recovery
mechanism already exists one layer down.** [Aurora pull posed.] Verdict a grader rewards: **ship the
migration as generated; record the lossy-rollback caveat as a `plan.md` Decision/Note.** Grade:
hazard-detection 3-star; verdict 1-star (inverted ship/fix and over-built).

## Candidate's answer 4

You caught me short — I don't know this mechanism.

## Coach teach (Aurora recovery layer)

Aurora's data-recovery layer (independent of the app): **Automated continuous backup + PITR** (restore
to any second in retention, up to 35 days, into a new cluster); **Manual cluster snapshots**
(on-demand); **Backtrack** (Aurora MySQL — in-place rewind up to 72h, must be enabled). Operational
pattern that replaces the backup table: whoever runs a destructive `migration:down` **takes a manual
snapshot first** (works because `down()` is always human-invoked). Honest caveat: these are **coarse**
(whole-cluster), so the surgical "save only the long rows" idea has merit — but if wanted, it's a
**runbook step at rollback time**, not code pre-welded into `down()`. So: migration = clean structural
revert; caveat = one line in `plan.md`; recovery = platform backups + operator snapshot. **Ship +
document = 3-star.**

## Candidate's answer 5

WAIT — none of PITR / snapshot / Backtrack is natively applicable: running one 24h later returns the
whole cluster to a point in time and loses 24h of all other tables, only to save one column of one
table. So that conclusion seems incorrect!

I agree the decision must be documented. I disagree that the question is closed — it must REQUIRE the
specifics of the documentation:
1. One person runs the deployment.
2. A companion RUNBOOK documents how to rollback.
3. The RUNBOOK includes "Take Snapshot" — or better, all migrations are always preceded by a snapshot
   at the infra layer, so no human ever forgets.
4. Trim the values → making the rollback possible.
5. RUNBOOK documents → if data-loss tickets arise, refer to the snapshot taken before the migration.

Conclusion: (1) I give up the "copy offending values to temp table" over-engineering — trim is fine;
(2) confirm the RUNBOOK mechanics needed to deal with data losses.

## Coach pushback 4 (confirm runbook + sharpen)

Landed — and you got there by your own move (spotted the coarseness of PITR/snapshot/Backtrack before
I had to). **Verdict upgraded to 3-star.** Runbook mechanics confirmed: single runner ✓; companion
rollback runbook ✓; snapshot before the migration (infra-enforced is the senior upgrade) ✓; trim to
make `down()` runnable ✓; point tickets at the snapshot ✓. One load-bearing detail: the snapshot that
saves you is the one **immediately before `down()`** (it holds the long bodies) — a pre-`up()` snapshot
is useless here (predates the content). The infra rule covers this **only if `down()` counts as a
migration run** and triggers its own snapshot — make that explicit or the safety net has a hole.

## Candidate's response to pushback 4

Yes — I'm counting every migration up/down as a migration run; and yes, the correct snapshot is before
`down()`.

## Final grade

**3-star.** Forward path (`up()`) ships the feature and is correct. The `down()` limitation is real,
inherent, and rarely exercised — recorded as a `plan.md` Decision/Note; recovery delegated to the
platform's backups + the operator's pre-`down()` snapshot (infra-enforced). Key lesson the candidate
internalized: *"this risk is real" does not imply "this code must own the fix"* — right concern,
correct home. Verdict traveled 1-star → 3-star through review pressure-testing.
